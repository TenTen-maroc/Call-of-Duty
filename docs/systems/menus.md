# Menus — main menu, pause, settings page

> Last verified: 2026-08-11
> **Verified in play:** no. Compiled, gated, and covered by 7 PlayMode tests
> (scene loads, panels present, timeScale, input blocking, settings reaching the
> camera). Whether the screens *read* well is a play question.

## Overview

Three screens and the two small pieces they share. Before this system the game
had no way in and no way out: `00_Boot` loaded straight into the grey box, there
was no mode selection, no pause, no settings, and the cursor never unlocked for
the whole session.

| Screen | Scene | Component |
| --- | --- | --- |
| Main menu | `20_MainMenu` | [MainMenuPanel](../../Assets/_Project/Scripts/UI/MainMenuPanel.cs) |
| Pause | `10_GreyBox` | [PausePanel](../../Assets/_Project/Scripts/UI/PausePanel.cs) |
| Settings | both | [SettingsPanel](../../Assets/_Project/Scripts/UI/SettingsPanel.cs) |

Shared: [MenuCursor](../../Assets/_Project/Scripts/UI/MenuCursor.cs) (which row is
selected) and [MenuInput](../../Assets/_Project/Scripts/UI/MenuInput.cs) (the keys).

## Scenes & Prefabs

All three are generated by `GreyBoxBuilder` — `BuildMainMenuScene`,
`BuildPauseUi`, and the shared `BuildMenuScreen` helper that lays out the
backdrop/title/body/footer every screen uses. `RegisterScenes` now registers
**three** scenes, and index 0 is `00_Boot`, which is what a built player loads.

`BootLoader._firstScene` is `20_MainMenu`.

**Draw order is load-bearing.** uGUI paints siblings in hierarchy order, so
`BuildPauseUi` is called *after* `BuildRunUi`: a pause menu created earlier is
painted underneath the shop it is meant to cover. The settings page is created
last for the same reason.

## Key Behaviors & Non-Obvious Patterns

### One input owner per screen

`SettingsPanel` has **no `Update`**. Its host — pause or the main menu — calls
`HandleInput()`. Two components polling the same Escape key in the same frame is
a race: MonoBehaviour execution order is undefined, so closing the settings page
could *also* unpause the game, or not, depending on the order Unity happened to
pick that session.

The same reasoning runs outward: `ShopPanel`, `GameOverPanel` and `CheatConsole`
each hold a `PausePanel` reference and ignore every key while paused. They share
keys with the pause menu — **SPACE** is "next wave" in the shop and "confirm" in
a menu; **R** is "restart" on the death screen and "reroll" in the shop.

### timeScale

`Pause()` **captures** `Time.timeScale` and `Resume()` restores what it found —
it never assumes 1. The sandbox console's slow-mo may already own the clock, and
resuming to a hard 1 would silently cancel a cheat the player turned on. There
is a PlayMode test for exactly this.

`fixedDeltaTime` is deliberately **not** scaled on pause. Slow-mo scales it to
keep physics in step with a slower clock; at `timeScale 0` no `FixedUpdate` runs
at all, and a `fixedDeltaTime` of 0 is a hang waiting to happen.

`RestoreTime()` runs in `OnDisable` too. A scene load while paused would
otherwise leave the *next* scene frozen at 0 with no panel to unfreeze it —
indistinguishable from a crash. `MainMenuPanel.Start` also sets `timeScale = 1`
as a belt-and-braces second line of defence, and a test asserts it.

### Input blocking

Pause calls `PlayerInput.SetBlocked(true)`, which disables the whole action map.
Every property on `PlayerInput` then reports "no input", so movement, look,
firing and reloading stop at their single source rather than each component
growing its own `if (paused)`. The flag survives a disable/enable cycle — a
component re-enabled while a menu is open must not hand control back.

### Cursor

`PlayerLook.SetCursorLocked(bool)` is the single owner. Pause and both menus call
it; nothing else touches `Cursor`.

## Modes

`GameMode` is `Run` or `Sandbox` — the two locked in CLAUDE.md. The choice is
carried from the menu to the game scene through **`SaveData.lastMode`**, not a
static field. A static would be the obvious carrier and is exactly what this
project bans: Domain Reload is off, so it would survive into the following Play
session and start a Run in Sandbox.

| | Run | Sandbox |
| --- | --- | --- |
| Starting money | `ShopConfig.startingMoney` (300) | `ShopConfig.sandboxStartingMoney` (100000) |
| Cheat console | off | on |
| Sets the record | yes | **no** |

**Why money is the whole of "everything unlocked".** In a game whose entire
progression is a shop, a parallel unlocked-inventory system would be a second way
to own a module and a second thing to keep in sync with the shop. One number in
an asset does the same job.

**`RecordRunEnded` refuses to write in Sandbox** ([RunContext](../../Assets/_Project/Scripts/Core/RunContext.cs)).
One accidental sandbox session would otherwise overwrite a real best round,
permanently.

**The cheat console's gate has two layers.** `#if UNITY_EDITOR ||
DEVELOPMENT_BUILD` removes it from a shipping build entirely. Inside a
development build, `Awake` additionally disables it unless the mode is Sandbox.
**The editor is exempt on purpose** — pressing Play straight into `10_GreyBox` is
how this project is tuned, and gating on whichever mode was last picked would
break that workflow for no safety gain, since an editor session can already edit
every asset in the game.

## Quitting to the menu records the run

Abandoning still calls `RunContext.RecordRunEnded()`. You reached that round
either way, and a record that only lands on death rewards suiciding to bank it —
the opposite of what a permadeath score is for.

## Gotchas

- **An `Object` handle does not survive a scene switch.** Closing a scene lets
  Unity unload every asset it was the last thing holding, and a C# handle to an
  unloaded `UnityEngine.Object` compares equal to `null`. `GreyBoxVerify` loads
  the menu scene's configs *after* opening that scene, and runs `VerifyMenuScene`
  *after* the grey box's own asset checks — opening the near-empty boot scene
  earlier made every `DroneConfig` read as "(missing asset)" while it sat
  perfectly fine on disk. This cost one build round.
- **The menu scene needs its own repair pass**, not just a check. Asset
  references assigned into a never-saved scene silently do not persist; the menu's
  `SettingsHub` holds two of them, and the first build produced them null.
- Menus are keyboard-driven with **no EventSystem**, matching `ShopPanel`'s
  existing, deliberate choice. Revisit when a gamepad is on the list — that is
  what a second action map is for, and `MenuInput` is the one file that changes.
- `MenuCursor.Move` adds `Count` before the modulo. C# `%` keeps the sign of the
  dividend, so `-1 % 4` is `-1`, and moving up from the first row would index out
  of range.
- `Cursor.lockState` is **never asserted in a test**. A `-batchmode` run has no
  window, so the platform ignores the request and the field reads `None`
  regardless of what the code did — the assertion would pass for the wrong reason
  in one place and fail for the wrong reason in another.
